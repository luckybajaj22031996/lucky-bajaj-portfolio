Insurance Platforms Compared
Product Teardown · PhonePe vs PolicyBazaar vs Ditto
Why This Analysis

Working in insurance at ThoughtWorks sparked a question: how are consumer-facing insurance platforms solving the same fundamental problem — getting people to buy insurance — through radically different product philosophies? I mapped three players who represent three distinct bets on how insurance distribution should work in India.

This teardown examines PhonePe (super-app, transaction-first), PolicyBazaar (comparison marketplace), and Ditto (advisory-first) — across UX, strategy, business model, and user journey depth.

The Three Players

Super-app · Transaction-first
Insurance embedded in payments — buy in 7 steps, minimal friction, auto-renewal via UPI
Bet: payments trust → financial products trust
PB

Marketplace · Comparison-first
40+ insurers, deep filters, price transparency — maximum choice for the informed buyer
Bet: more options → better decisions → loyalty
DT
Ditto
Advisory · Education-first
Human advisors, 30-min calls, curated 2-3 recommendations — depth over breadth
Bet: understanding → trust → lifetime value

User Journey Comparison — Interactive

Click each platform to explore their user journey:

PhonePe — 7 Steps (Ruthlessly Streamlined)
Entry → DOB + Income → Recommendations → Plan Selection → Add-ons → KYC → Payment. Every screen optimized for conversion over comprehension. The bet: mobile-native users value speed over education.
PolicyBazaar — 12+ Steps (Maximizing Basket Value)
Extended form (pincode, city, marital status, existing policies) → deep comparison filters → multiple upsells (Limited Pay, spouse cover) → checkout. Optimized for transaction value through urgency and choice overload.
Ditto — 3 Steps + 30-Min Call (Deliberate Friction)
Interest form → advisor scheduling → consultation → curated recommendation. Friction is a feature — signals that insurance deserves deliberation. Filters serious buyers, enables premium service model.
Key Insight: Step count is a strategic choice, not a UX failure. Each platform optimizes for different outcomes: conversion rate (PhonePe), basket size (PolicyBazaar), or decision quality (Ditto).
Business Model Implications

PhonePe: Low CAC (organic from payments app) + high volume + recurring AutoPay premiums. First-year commission (~₹16K on ₹52K premium) pays for acquisition. Trail commissions (years 2–30) are near-pure profit. Cross-sell funnel: insurance → investments → loans.

PolicyBazaar: Moderate CAC (performance marketing) + conversion optimization via upsells. "Limited Pay" upsell doubles premium (₹1,350 → ₹2,786) with higher commission. Add-ons (spouse cover: +₹567/mo) inflate average transaction value. Scale through paid acquisition.

Ditto: High CAC (advisor call costs ~₹500–1,000) + premium customer required. Economics only work if: customers buy ₹5Cr+ sum assured policies, claims success drives referrals, and lifetime support justifies positioning. This is a relationship business, not a transaction business.

5 PM Lessons (Distilled)
1. Build on your moatPhonePe = UPI infrastructure. PolicyBazaar = insurer partnerships. Ditto = human expertise. Don't copy competitors — double down on your unfair advantage.
2. Friction is a product decisionDitto deliberately slows users to filter buyers and enable premium service. Sometimes friction increases quality and LTV.
3. Education vs. speed is binaryChoose your customer first, then optimize. Trying to serve everyone well serves no one well.
4. Trust signals vary by audienceBrand (PhonePe), price guarantee (PolicyBazaar), expert credibility (Ditto). Different segments need different proof points.
5. Economics dictate productPhonePe's volume model needs automation. Ditto's high-CAC needs premium customers. Your unit economics determine your product constraints.
Untapped opportunityAll three show same flow to everyone. First-time buyer vs. switcher need different experiences — personalization layer is missing.

Nutrition labels are information-heavy but decision-poor. Consumers face a wall of numbers — calories, macros, ingredient lists — with no clear signal on whether a product is suitable for them. Key Design Decisions & Tradeoffs

Prompt-based scoring over rigid rules: Rather than fixed thresholds (e.g. "sugar > 10g = bad"), the product uses AI-guided reasoning — enabling nuanced trade-offs like high fat but high protein in a nut bar. This sacrifices some consistency for realistic, contextual judgement.

Mobile-first, minimal inputs: Deliberate choice to require zero mandatory inputs at launch. Personalization is opt-in. This reduces friction at first use, with the tradeoff of less tailored early scores — acceptable given the discovery goal.

Category-awareness over universal scoring: A 5g sugar biscuit is very different from a 5g sugar fruit — context-aware judgement prevents misleading verdicts, though it adds prompt complexity.

Commute Optimization System
Data Engineering · Personal Analytics · Powai ↔ Andheri, Mumbai
Problem Statement

My Powai ↔ Andheri commute varied by 30–40 minutes depending on departure time, yet every decision was based on intuition. Without historical data, it was impossible to distinguish real traffic patterns from perceived randomness — and every suboptimal departure meant avoidable time lost.

User Personas
LB
Lucky — Primary User
Daily commuter, consultant
Wants to leave at the optimal time without manually checking maps each day
"I'm making a 45-min vs 20-min decision with zero data."
UC
Urban Commuter — Extensible
Any high-traffic city resident
Reusable framework for any route with significant travel-time variability
"Google Maps tells me current duration, not the best time to leave."
Hypothesis

"If I collect enough timestamped travel duration data across different departure windows, I can identify statistically reliable patterns that reveal an optimal departure window — reducing average commute time without changing the route."

Solution Architecture
1
Data Acquisition
Google Maps Directions API — queried duration_in_traffic with live departure timestamps for both route directions
2
Automation Pipeline
Python script fetches at fixed intervals, converts to IST, appends to CSV — runs via GitHub Actions (cloud) and cron jobs (local) with zero manual intervention
3
Analysis Layer
Trend visualization, time-window filtering, peak vs. off-peak comparison, and directional pattern analysis
4
Decision Output
Identify departure windows with consistently lowest travel duration — targeted for eventual push alerts
Outcomes
✓
Automated pipeline built & running
2
Route directions tracked
0
Manual data entry required
∞
Reusable for any city/route
Key Learnings
  • Traffic variability is quantifiable: Duration swings were larger and more predictable than intuition suggested
  • Directionality matters: Powai→Andheri and Andheri→Powai have meaningfully different congestion fingerprints by hour
  • Small datasets mislead: Early patterns required weeks of validation before acting — a core PM lesson about premature conclusions
  • Automation removes behavioural bias: Scheduled collection removes the human tendency to only check when it feels convenient

MealTime — Meal-Time Content Curator
AI · Content Recommendation · 0→1 · Shipped MVP
Problem Statement

Every lunch and dinner is a 10–45 minute lean-back window. People want something good on screen — but every platform they open is optimised for binge sessions, not meal-sized viewing. The result: endless scrolling, defaulting to the same rewatch, or giving up entirely.

The gap isn't content quality — it's discovery under time pressure. Nobody can recall what they'd actually enjoy when the food is getting cold and decision fatigue kicks in. Availability beats preference every time.

CS

Solution & How It Works

MealTime is a recommendation layer — not a streaming platform. It sits on top of YouTube and existing OTT apps, surfacing exactly 5 picks per meal session.

1
Taste Profiling
6 forced-choice cards across genres + 2 preference questions. Takes ~90 seconds. Builds a weighted tag vector.
2
Mood Selection
4 modes: "For you" (taste-dominant), "Make me laugh", "Make me think", "Just chill". Dynamic weight allocation per mode.
3
Scoring & Ranking
Each of 200 content pieces scored across 6 dimensions: quality, duration fit, tag match, genre match, novelty, and mood fit.
4
5 Picks + Reason
Weighted reservoir sampling from top 12 candidates. Each pick comes with a personalised reason line. Optional AI mode (Claude) for even sharper picks.
Scoring Engine

Two-mode dynamic weight system. In "For you" mode, taste vector drives 33% of the score — the biggest single factor. When a specific mood is active, mood fit jumps to 48% and taste drops to 12%.

Mood filtering is tag-based, not genre-based. Each content piece is scored 0–100 for mood fit using boost/penalty tag lists. A funny Drama surfaces in laugh mode. A boring Comedy sinks. Genre is a tiebreaker, not a gate.

Duration uses an asymmetric Gaussian curve — short content is penalised gently (you can watch another one), long content penalised harder (you can't finish it).

Key Design Decisions

Tag-based mood filtering over genre exclusion: The original approach excluded entire genres per mood (all Drama blocked in laugh mode). This created false negatives — funny Dramas hidden, unfunny Travel content showing. Switching to per-item tag scoring fixed accuracy without losing the mood constraint.

Dynamic weight allocation: A user's taste profile and their current mood can conflict. When mood is active, it takes 48% of the score so it can't be overridden by taste. In "For you" mode, taste gets 33%. Clean separation, no contradictions.

BYOK AI model: Claude API adds personalised reason lines and smarter taste profiling. But the app works fully without it — hardcoded scoring is the default. AI is an enhancement layer, not a dependency. Cost: less than ₹1 per session.

Search-intent URLs over deep links: Instead of direct platform links (which break when content moves), every recommendation links to a YouTube or Google search for that specific title. Slightly more friction, zero broken links.

Agent Forge
AI · Open Source · Developer Tools · Multi-Agent Scaffolding
Problem

Multi-agent AI systems sound complex, and the ecosystem makes them feel that way. Frameworks like LangChain, CrewAI, and AutoGen add abstraction layers that obscure a simple truth: a multi-agent pipeline is just prompt files, a shell script, and the filesystem. Developers who want to experiment face two options: learn a complex framework, or figure out the orchestration pattern from scratch. Both slow you down before you've started on the actual problem.

The Insight

After studying real-world multi-agent systems (including viral examples like autonomous stock portfolio managers running 30+ agents in parallel), I noticed the underlying pattern is always the same:

  • Agents = Claude Code sessions with specific instructions (prompt files)
  • Orchestrator = A bash script running agents in sequence or parallel
  • Communication = Agents read/write files, the filesystem is the message bus
  • Scheduling = Cron or GitHub Actions triggers the whole thing autonomously

If the pattern is this consistent, it should be scaffoldable. That's what Agent Forge does.

How It Works
1
Describe your use case
Tell Claude you want a multi-agent system. Agent Forge asks about your domain, coordination pattern (sequential/parallel/mixed), and scheduling needs.
2
Review the architecture
Agent Forge proposes the agent list, data flow, and execution order. You approve or adjust before any files are generated.
3
Get the complete project
It generates everything: CLAUDE.md (shared context), prompt files per agent, orchestrator script with parallel support, data/output directories, GitHub Actions config, and a README.
4
Run it
bash scripts/run-pipeline.sh — the pipeline executes, agents hand off work through files, output lands in the output folder.
What Gets Generated

├── CLAUDE.md              # Shared context every agent reads
├── README.md              # How to run and customize
├── prompts/               # One .md file per agent

├── data/                  # Agents communicate through files
└── output/                # Final deliverables
Example Use Cases
Market ResearchScan financials, score stocks, bull/bear analysis (parallel), portfolio report
Content PipelineScan news, rank topics, generate outlines + social posts (parallel), daily digest
Code ReviewFetch PR diff, quality + security + test audit (parallel), consolidated review
Competitive IntelCollect data, analyze positioning, SWOT analysis, strategy recommendations
Key Design Decisions

No framework, by design. The orchestrator is a bash script. Agents are markdown prompt files. Communication is the filesystem. Complexity kills adoption. Anyone who can write a prompt can build a multi-agent system.

Files as the message bus. One agent writes JSON, the next reads it. No databases, no queues. Every agent is independently testable.

Interactive scaffolding over static templates. The skill asks about your specific use case and generates custom prompt content, not blank templates.

Parallel support built in. The orchestrator handles sequential and parallel execution with proper process management and failure detection.
